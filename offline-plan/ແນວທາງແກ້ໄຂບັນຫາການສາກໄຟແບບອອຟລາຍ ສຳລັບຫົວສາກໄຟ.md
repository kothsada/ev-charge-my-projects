# **ແນວທາງແກ້ໄຂບັນຫາການສາກໄຟແບບອອຟລາຍ ສຳລັບຫົວສາກໄຟ**

## **1、ຄວາມເປັນມາຂອງບັນຫາ**

ບັນຫາປັດຈຸບັນ:

* ເມື່ອຂາດເຄືອຂ່າຍ 5 ນາທີ ຈະບັງຄັບຢຸດການສາກໄຟ, ຜູ້ໃຊ້ຕ້ອງສະແກນ QR ຄືນໃໝ່

ເປົ້າໝາຍການປັບປຸງ:

* ໃນໄລຍະຂາດເຄືອຂ່າຍ ໃຫ້ສາກໄຟຕໍ່ໄປໄດ້, ບໍ່ມີການບັງຄັບຢຸດຍ້ອນເວລາຄົບກຳນົດ  
* ຜ່ານ RemoteStartTransaction ເພື່ອສົ່ງຂອບເຂດຈຳກັດຍອດເງິນ, ໃຫ້ຫົວສາກໄຟຄວບຄຸມດ້ວຍຕົນເອງໃນທ້ອງຖິ່ນ  
* ເມື່ອເຄືອຂ່າຍກັບຄືນມາ ໃຫ້ຄິດໄລ່ຄ່າສາກແບບອັດຕະໂນມັດ

---

## **2、ແນວທາງດ້ານເຕັກນິກ**

### **2.1 ຂັ້ນຕອນການເຮັດວຽກໂດຍລວມ**

`text`

`ຜູ້ໃຊ້ App → ສ້າງຄຳສັ່ງຊື້ → CSMS → RemoteStartTransaction(ພ້ອມຂອບເຂດຈຳກັດຍອດເງິນ) → ຫົວສາກໄຟ`  
`↓`  
`ເລີ່ມສາກໄຟ (ອອນລາຍ/ອອຟລາຍ)`  
`↓`  
`ຂາດເຄືອຂ່າຍ → ຫົວສາກໄຟສາກຕໍ່ໄປໃນທ້ອງຖິ່ນ`  
`↓`  
`ຮອດເງື່ອນໄຂຢຸດ → ຢຸດ, ເກັບຂໍ້ມູນຊົ່ວຄາວ`  
`↓`

`ເຄືອຂ່າຍກັບຄືນ → StopTransaction → ຄິດໄລ່ຄ່າສາກແບບອັດຕະໂນມັດ`

### **2.2 ການຂະຫຍາຍຟີລດແບບກຳນົດເອງໃນ RemoteStartTransaction**

`json`

`[2, "msg-id-001", "RemoteStartTransaction", {`  
`"connectorId": 1,`  
`"idTag": "USER-123456",`  
`"maxEnergyWh": 10000 // 【ເພີ່ມໃໝ່】ປະລິມານໄຟສາກສູງສຸດ (Wh)`

`}]`

ຄຳອະທິບາຍຟີລດ:

| ຟີລດ | ປະເພດ | ຄຳອະທິບາຍ |
| :---- | :---- | :---- |
| maxEnergyWh | number | ປະລິມານໄຟສາກສູງສຸດ (Wh), ເມື່ອຫົວສາກໄຟສະສົມໄດ້ຄ່ານີ້ຈະຢຸດອັດຕະໂນມັດ |

ໝາຍເຫດ: `maxEnergyWh` ເປັນຟີລດທີ່ບໍ່ໄດ້ກຳນົດມາດຕະຖານໃນ OCPP, ຕ້ອງການໃຫ້ຜູ້ຜະລິດຫົວສາກໄຟຊ່ວຍປັບປຸງເພື່ອຮັບການແປຄ່າ.

### **2.3 ສະຖານະການເຄື່ອນໄຫວຂອງລາຍການຊື້**

`text`

`ACTIVE → PROCESSING → COMPLETED`  
`↑ │`  
`│ └── StopTransaction ຊ້ຳ ເພື່ອອັບເດດຂໍ້ມູນ meter`

`└── ຮັກສາສະຖານະນີ້ໄວ້ໃນໄລຍະຂາດເຄືອຂ່າຍ`

### **2.4 ຍຸດທະສາດການຈັດການແບບອອຟລາຍ**

| ໄລຍະ | ການດຳເນີນງານ |
| :---- | :---- |
| ກວດພົບຂາດເຄືອຂ່າຍ (15 ວິນາທີ) | ໝາຍສະຖານະ OFFLINE, ແຈ້ງຜູ້ໃຊ້ "ກຳລັງສາກໄຟແບບອອຟລາຍ" |
| ສາກໄຟແບບອອຟລາຍ (ບໍ່ຈຳກັດເວລາ) | ຄຳສັ່ງຊື້ຮັກສາສະຖານະ ACTIVE, ຫົວສາກໄຟຄວບຄຸມໃນທ້ອງຖິ່ນ |
| ເຄືອຂ່າຍກັບຄືນ | ຮັບ StopTransaction, ຄິດໄລ່ຄ່າສາກແບບອັດຕະໂນມັດ |

## **3、ແນວທາງການປັບປຸງລະຫັດ**

ຄຳອະທິບາຍ: ຂ້າງລຸ່ມນີ້ແມ່ນແນວທາງ ແລະ ເຫດຜົນຫຼັກໃນການປັບປຸງ, ການຈັດຕັ້ງປະຕິບັດຕົວຈິງ ກະລຸນາປັບຕາມໂຄງສ້າງລະຫັດປັດຈຸບັນ.

### **3.1 ການປັບປຸງຖານຂໍ້ມູນ**

ເປົ້າໝາຍ: ຮອງຮັບການເກັບຂອບເຂດຈຳກັດຍອດເງິນ ແລະ ກົນໄກການຫັກຄ່າລ່ວງໜ້າ

ເຫດຜົນການປັບປຸງ:

* ຕາຕະລາງລາຍການຊື້ ເພີ່ມຟີລດ «ປະລິມານໄຟສາກສູງສຸດ», ບັນທຶກຂອບເຂດຈຳກັດຍອດເງິນທີ່ສົ່ງໃຫ້ຫົວສາກໄຟ  
* ຕາຕະລາງກະເປົາເງິນ ເພີ່ມຟີລດ «ຍອດເງິນທີ່ຖືກລັອກ», ໃຊ້ສຳລັບການຫັກຄ່າລ່ວງໜ້າ  
* ຕາຕະລາງຄຳສັ່ງຊື້ ເພີ່ມຟີລດ «ຄ່າໃຊ້ຈ່າຍທີ່ຄາດການ» ແລະ «ຄ່າໃຊ້ຈ່າຍຕົວຈິງ»

### **3.2 ກຳຈັດການບັງຄັບຢຸດຍ້ອນເວລາຄົບກຳນົດແບບອອຟລາຍ**

ເປົ້າໝາຍ: ເມື່ອຂາດເຄືອຂ່າຍ ໃຫ້ຄຳສັ່ງຊື້ຮັກສາສະຖານະ ACTIVE, ບໍ່ບັງຄັບຢຸດ

ເຫດຜົນການປັບປຸງ:

* ຍົກເລີກເຫດຜົນການບັງຄັບຢຸດ 5 ນາທີແບບອອຟລາຍເດີມ  
* ປ່ຽນເປັນກວດພົບຂາດເຄືອຂ່າຍ 15 ວິນາທີ, ພຽງແຈ້ງຜູ້ໃຊ້ "ກຳລັງສາກໄຟແບບອອຟລາຍ", ຄຳສັ່ງຊື້ຮັກສາສະຖານະ ACTIVE

### **3.3 ປັບປຸງການຈັດການ StopTransaction**

ເປົ້າໝາຍ: ຮອງຮັບການລາຍງານຊ້ຳ ແລະ ການເຄື່ອນຍ້າຍສະຖານະ ຫຼັງຈາກເຊື່ອມຕໍ່ຄືນ

ເຫດຜົນການປັບປຸງ:

* ສະຖານະ COMPLETED ເມື່ອຮັບ StopTransaction, ພຽງອັບເດດຂໍ້ມູນ meter ເທົ່ານັ້ນ  
* ສະຖານະ ACTIVE ເມື່ອຮັບ StopTransaction, ປ່ຽນເປັນສະຖານະ PROCESSING ແລະ ເລີ່ມຄິດໄລ່ຄ່າສາກ  
* ສະຖານະ PROCESSING ເມື່ອຮັບ StopTransaction, ອັບເດດຂໍ້ມູນ meter

### **3.4 ການຂະຫຍາຍ RemoteStartTransaction**

ເປົ້າໝາຍ: ສົ່ງຂອບເຂດຈຳກັດຍອດເງິນໃຫ້ຫົວສາກໄຟ

ເຫດຜົນການປັບປຸງ:

* ໃນການສົ່ງ RemoteStartTransaction, ໃຫ້ບັນຈຸຟີລດທີ່ກຳນົດເອງ `maxEnergyWh`  
* ສົ່ງພຽງປະລິມານໄຟສາກສູງສຸດເທົ່ານັ້ນ, ບໍ່ສົ່ງລາຄາຕໍ່ຫົວໜ່ວຍ

### **3.5 ການຄາດການຍອດເງິນ**

ເປົ້າໝາຍ: ປ້ອງກັນຍອດເງິນບໍ່ພຽງພໍ, ຮັບປະກັນວ່າໃນໄລຍະສາກໄຟແບບອອຟລາຍມີຍອດເງິນພຽງພໍ

ເຫດຜົນການປັບປຸງ:

* ເມື່ອສ້າງຄຳສັ່ງຊື້ ໃຫ້ໃຊ້ກົນໄກລັອກແບບກະຈາຍ (Distributed Lock) ເພື່ອປ້ອງກັນການສ້າງພ້ອມກັນຫຼາຍລາຍການ ຈົນເຮັດໃຫ້ຍອດເງິນບໍ່ພຽງພໍ

### **3.6 ວຽກຕາມເວລາກຳນົດ**

ເປົ້າໝາຍ: ທຳຄວາມສະອາດຄຳສັ່ງຊື້ທີ່ຜິດປົກກະຕິ, ຕິດຕາມຄຳສັ່ງຊື້ທີ່ຍັງບໍ່ທັນຄິດໄລ່ຄ່າສາກເປັນເວລາດົນ

ເຫດຜົນການປັບປຸງ:

* ຕັ້ງຄ່າວຽກຕາມເວລາເພື່ອທຳຄວາມສະອາດຄຳສັ່ງຊື້ທີ່ຍັງຄົງສະຖານະ ACTIVE ເກີນ 24 ຊົ່ວໂມງ  
* ຕັ້ງຄ່າວຽກຕາມເວລາເພື່ອກວດສອບບັນຊີ, ສົ່ງການແຈ້ງເຕືອນສຳລັບຄຳສັ່ງຊື້ທີ່ຍັງບໍ່ທັນຄິດໄລ່ຄ່າສາກເກີນ 4 ຊົ່ວໂມງ

## **4、ລາຍການທີ່ຜູ້ຜະລິດອຸປະກອນຕ້ອງປະສານງານ**

\*\*ເນື້ອໃນລຸ່ມນີ້ ຕ້ອງການໃຫ້ຜູ້ຜະລິດຫົວສາກໄຟຊ່ວຍປະຕິບັດ, ສິ່ງທີ່ໝາຍ 【ມີແລ້ວ】 ແມ່ນຄວາມສາມາດທີ່ມີຢູ່ແລ້ວ, 【ຄັ້ງນີ້ເພີ່ມໃໝ່】 ແມ່ນສິ່ງທີ່ຕ້ອງພັດທະນາ ຫຼື ປັບປຸງໃໝ່

### **4.1 【ຄັ້ງນີ້ເພີ່ມໃໝ່】ການແປຄ່າຟີລດທີ່ກຳນົດເອງໃນ RemoteStartTransaction**

ຄວາມຕ້ອງການ: ເມື່ອຫົວສາກໄຟໄດ້ຮັບຂໍ້ຄວາມ RemoteStartTransaction, ນອກຈາກການແປຄ່າຟີລດມາດຕະຖານແລ້ວ, ຕ້ອງແປຄ່າຟີລດທີ່ກຳນົດເອງ `maxEnergyWh`

ຂໍ້ກຳນົດການແປຄ່າ:

| ຂັ້ນຕອນ | ການດຳເນີນງານ | ຄຳອະທິບາຍ |
| :---- | :---- | :---- |
| 1 | ແປຄ່າຟີລດມາດຕະຖານ | ແປຄ່າ `connectorId`, `idTag`, ປະຕິບັດຂັ້ນຕອນການເລີ່ມສາກມາດຕະຖານ |
| 2 | ແປຄ່າຟີລດທີ່ກຳນົດເອງ | ແປຄ່າ `maxEnergyWh` (ປະລິມານໄຟສາກສູງສຸດ, ຫົວໜ່ວຍ: Wh), ບັນທຶກໄວ້ໃນບໍລິບົດການຊື້ຂາຍປັດຈຸບັນ |
| 3 | ສົ່ງຄຳຕອບ | ສົ່ງຄຳຕອບມາດຕະຖານ, ບໍ່ໄດ້ຮັບຜົນກະທົບຈາກຟີລດທີ່ກຳນົດເອງ |

ຮູບແບບຄຳຕອບ:

`json`

`[3, "msg-id-001", { "status": "Accepted" }]`

ຄຳອະທິບາຍຟີລດ:

| ຟີລດ | ປະເພດ | ຫົວໜ່ວຍ | ຄຳອະທິບາຍ |
| :---- | :---- | :---- | :---- |
| maxEnergyWh | number | Wh (ວັດ-ຊົ່ວໂມງ) | ປະລິມານໄຟສາກສູງສຸດທີ່ຄິດໄລ່ຈາກຍອດເງິນທີ່ຜູ້ໃຊ້ມີ, ເມື່ອຫົວສາກໄຟສະສົມໄດ້ຄ່ານີ້ ຕ້ອງຢຸດການສາກໄຟໂດຍອັດຕະໂນມັດ |

ວິທີຄິດໄລ່ (ຝ່າຍ Server):

`maxEnergyWh = floor(ຍອດເງິນ × ຄ່າຄວາມປອດໄພ ÷ ລາຄາຕໍ່ຫົວໜ່ວຍ × 1000)`

* ຄ່າຄວາມປອດໄພ: ຜູ້ໃຊ້ທົ່ວໄປ 0.8, ຜູ້ໃຊ້ VIP 0.9  
* ລາຄາຕໍ່ຫົວໜ່ວຍ: ລາຄາສາກໄຟທີ່ສະຖານີກຳນົດ (ບາດ/kWh)

### **4.2 【ມີແລ້ວ, ຕ້ອງຢືນຢັນ】ປະລິມານໄຟສາກສະສົມໃນທ້ອງຖິ່ນ**

ຄວາມຕ້ອງການ: ໃນລະຫວ່າງການສາກໄຟ ໃຫ້ສະສົມປະລິມານໄຟສາກແບບທັນສະພາບ

ການຢືນຢັນສະຖານະປັດຈຸບັນ: ກະລຸນາໃຫ້ຜູ້ຜະລິດຢືນຢັນວ່າຫົວສາກໄຟມີຄວາມສາມາດດັ່ງຕໍ່ໄປນີ້ແລ້ວຫຼືຍັງ:

* ໃນລະຫວ່າງການສາກໄຟ ມີການສະສົມຄ່າ meter (ຫົວໜ່ວຍ: Wh)  
* ຄ່າສະສົມຕ້ອງຖືກເກັບໄວ້ແບບຖາວອນ (Persistent Storage) ເພື່ອປ້ອງກັນການສູນເສຍເມື່ອໄຟດັບ

ຂໍ້ກຳນົດການປັບປຸງຄັ້ງນີ້ (ຖ້າຄວາມສາມາດທີ່ມີຢູ່ແລ້ວບໍ່ພຽງພໍ ຕ້ອງປັບປຸງ):

* ເລີ່ມແຕ່ເວລາເລີ່ມສາກໄຟ, ສະສົມຄ່າ meter ແບບທັນສະພາບ (ຫົວໜ່ວຍ: Wh)  
* ຄ່າສະສົມ \= ຄ່າ meter ປັດຈຸບັນ \- ຄ່າ meterStart ຕອນເລີ່ມສາກ  
* ອັບເດດຄ່າສະສົມທຸກໆ 10 ວິນາທີ  
* ຄ່າສະສົມຕ້ອງຖືກເກັບໄວ້ແບບຖາວອນ ເພື່ອປ້ອງກັນການສູນເສຍເມື່ອໄຟດັບ

### **4.3 【ຄັ້ງນີ້ເພີ່ມໃໝ່】ຢຸດອັດຕະໂນມັດເມື່ອຍອດເງິນໝົດ**

ຄວາມຕ້ອງການ: ເມື່ອປະລິມານໄຟສາກສະສົມຮອດ `maxEnergyWh`, ຫົວສາກໄຟຕ້ອງຢຸດການສາກໄຟໂດຍອັດຕະໂນມັດ

ເຫດຜົນການຢຸດ:

`text`

`ຖ້າ ປະລິມານໄຟສາກສະສົມ ≥ maxEnergyWh, ໃຫ້ຢຸດການສາກໄຟໂດຍອັດຕະໂນມັດ ແລະ ສົ່ງ StopTransaction`

ລຳດັບຄວາມສຳຄັນຂອງເງື່ອນໄຂການຢຸດ:

1. ປະລິມານໄຟສາກຮອດຂອບເຂດຈຳກັດຍອດເງິນ (ປະລິມານສະສົມ ≥ maxEnergyWh) —— ຄັ້ງນີ້ເພີ່ມໃໝ່  
2. ໝໍ້ໄຟ EV ເຕັມ (SoC=100%)  
3. ຜູ້ໃຊ້ຢຸດດ້ວຍຕົນເອງ (App/ປຸ່ມ)  
4. ຫົວສາກໄຟເກີດຂໍ້ຜິດພາດ (ຮ້ອນເກີນ, ກະແສໄຟຟ້າເກີນ ແລະ ອື່ນໆ)  
5. ຢຸດສຸກເສີນ

### **4.4 【ມີແລ້ວ, ຕ້ອງຢືນຢັນ】ການເກັບຂໍ້ມູນຊົ່ວຄາວແບບອອຟລາຍ**

ຄວາມຕ້ອງການ: ໃນໄລຍະຂາດເຄືອຂ່າຍ ຕ້ອງເກັບຂໍ້ມູນການສາກໄຟໄວ້ຊົ່ວຄາວ, ເພື່ອຮັບປະກັນວ່າເມື່ອເຄືອຂ່າຍກັບຄືນມາ ສາມາດລາຍງານໄດ້ຢ່າງຄົບຖ້ວນ

ການຢືນຢັນສະຖານະປັດຈຸບັນ: ກະລຸນາໃຫ້ຜູ້ຜະລິດຢືນຢັນວ່າຫົວສາກໄຟມີຄວາມສາມາດດັ່ງຕໍ່ໄປນີ້ແລ້ວຫຼືຍັງ:

* ໃນໄລຍະຂາດເຄືອຂ່າຍ ສາມາດເກັບຂໍ້ມູນການສາກໄຟໄວ້ຊົ່ວຄາວ  
* ໃຊ້ຫົວໜ່ວຍຄວາມຈຳແບບບໍ່ລະເຫີຍ (Non-volatile Memory \- Flash/SD Card)

ຂໍ້ກຳນົດການປັບປຸງຄັ້ງນີ້ (ຖ້າຄວາມສາມາດທີ່ມີຢູ່ແລ້ວບໍ່ພຽງພໍ ຕ້ອງປັບປຸງ):

| ລາຍການ | ຂໍ້ກຳນົດ |
| :---- | :---- |
| ຄວາມຖີ່ຂອງການເກັບຊົ່ວຄາວ | ເກັບຂໍ້ມູນການສາກໄຟທຸກໆ 5 ນາທີ |
| ເນື້ອໃນທີ່ເກັບຊົ່ວຄາວ | meterStart, ປະລິມານໄຟສາກສະສົມປັດຈຸບັນ, ໄລຍະເວລາສາກ, ຄ່າເວລາ (Timestamp) |
| ສື່ກາງຈັດເກັບ | Flash/SD Card (ຫົວໜ່ວຍຄວາມຈຳແບບບໍ່ລະເຫີຍ) |
| ຮູບແບບຂໍ້ມູນ | ຮູບແບບ JSON, ພ້ອມຄ່າ Checksum |
| ວົງຈອນການເກັບຊົ່ວຄາວ | ຢ່າງໜ້ອຍ 7 ວັນ |

### **4.5 【ມີແລ້ວ, ຕ້ອງປັບ】ການລາຍງານເມື່ອເຄືອຂ່າຍກັບຄືນ**

ຄວາມຕ້ອງການ: ເມື່ອເຄືອຂ່າຍກັບຄືນມາ, ຫົວສາກໄຟຕ້ອງສົ່ງ StopTransaction ໂດຍອັດຕະໂນມັດ ເພື່ອລາຍງານຂໍ້ມູນການສາກໄຟ

ການຢືນຢັນສະຖານະປັດຈຸບັນ: ກະລຸນາໃຫ້ຜູ້ຜະລິດຢືນຢັນວ່າຫົວສາກໄຟມີຄວາມສາມາດໃນການລາຍງານອັດຕະໂນມັດເມື່ອເຄືອຂ່າຍກັບຄືນມາແລ້ວຫຼືຍັງ

ຂໍ້ກຳນົດການປັບປຸງຄັ້ງນີ້ (ຖ້າຄວາມສາມາດທີ່ມີຢູ່ແລ້ວບໍ່ພຽງພໍ ຕ້ອງປັບປຸງ):

* ເມື່ອກວດພົບວ່າເຄືອຂ່າຍກັບຄືນມາ, ສົ່ງ StopTransaction ໂດຍອັດຕະໂນມັດ  
* ຂໍ້ມູນທີ່ລາຍງານຕ້ອງມີ meterStart, meterStop, timestamp ແລະ ຂໍ້ມູນອື່ນໆຢ່າງຄົບຖ້ວນ

ຂັ້ນຕອນການລາຍງານ:

1. ກວດພົບວ່າເຄືອຂ່າຍກັບຄືນມາ  
2. ອ່ານຂໍ້ມູນການສາກໄຟທີ່ເກັບໄວ້ຊົ່ວຄາວ  
3. ກວດສອບຄວາມສົມບູນຂອງຂໍ້ມູນ  
4. ສົ່ງຂໍ້ຄວາມ StopTransaction

ຕົວຢ່າງຂໍ້ຄວາມ StopTransaction:

`json`

`[2, "msg-id-002", "StopTransaction", {`  
`"transactionId": 12345,`  
`"meterStop": 15000,`  
`"timestamp": "2026-07-24T10:30:00.000Z",`  
`"reason": "Local"`

`}]`

### **4.6 【ຄັ້ງນີ້ເພີ່ມໃໝ່】ການກວດສອບຄວາມສົມບູນຂອງຂໍ້ມູນ**

ຄວາມຕ້ອງການ: ເມື່ອເຄືອຂ່າຍກັບຄືນມາ, ຕ້ອງກວດສອບຄວາມສົມບູນຂອງຂໍ້ມູນທີ່ເກັບໄວ້ຊົ່ວຄາວ, ເພື່ອປ້ອງກັນຂໍ້ມູນເສຍຫາຍ

ຂໍ້ກຳນົດການກວດສອບ:

* ຄິດໄລ່ Checksum: ໃຊ້ MD5/SHA1 ກັບຂໍ້ມູນທີ່ເກັບໄວ້ຊົ່ວຄາວ  
* ປຽບທຽບ Checksum: ເມື່ອເຄືອຂ່າຍກັບຄືນມາ ໃຫ້ປຽບທຽບ Checksum ຂອງຂໍ້ມູນທີ່ເກັບໄວ້ຊົ່ວຄາວ  
* ການຟື້ນຟູຂໍ້ມູນ: ຖ້າການກວດສອບລົ້ມເຫລວ, ໃຫ້ພະຍາຍາມຟື້ນຟູຈາກ Backup; ຖ້າບໍ່ສາມາດຟື້ນຟູໄດ້ ໃຫ້ໝາຍເປັນຂໍ້ມູນຜິດປົກກະຕິ ແລະ ລາຍງານ  
* ການຈັດການຂໍ້ມູນຜິດປົກກະຕິ: ເມື່ອຂໍ້ມູນຜິດປົກກະຕິ ໃຫ້ສົ່ງ StopTransaction, ກຳນົດ reason ເປັນ "Local", ແລະ ໃນ meterValues ໃຫ້ມີຄຳອະທິບາຍຄວາມຜິດປົກກະຕິນຳ

### **4.7 【ຄັ້ງນີ້ເພີ່ມໃໝ່】ຂໍ້ກຳນົດການທົດສອບ**

ຜູ້ຜະລິດຕ້ອງປະສານງານເພື່ອທົດສອບດັ່ງຕໍ່ໄປນີ້:

| ສະຖານະການທົດສອບ | ເນື້ອໃນການທົດສອບ | ຜົນທີ່ຄາດຫວັງ |
| :---- | :---- | :---- |
| ສາກໄຟປົກກະຕິ | ຂັ້ນຕອນການສາກໄຟແບບຄົບວົງຈອນໃນສະພາບອອນລາຍ | ສາກໄຟເລີ່ມ ແລະ ຢຸດໄດ້ປົກກະຕິ |
| ສາກໄຟແບບອອຟລາຍ | ຈຳລອງການຂາດເຄືອຂ່າຍຫຼາຍຊົ່ວໂມງ | ຫົວສາກໄຟສາກຕໍ່ໄປໃນທ້ອງຖິ່ນ, ປະລິມານໄຟສາກສະສົມປົກກະຕິ |
| ຍອດເງິນໝົດ | ຕັ້ງຄ່າ maxEnergyWh ນ້ອຍ, ທົດສອບການຢຸດອັດຕະໂນມັດ | ເມື່ອປະລິມານໄຟສາກສະສົມຮອດຂອບເຂດຈຳກັດ ຈະຢຸດອັດຕະໂນມັດ |
| ການຄິດໄລ່ຄ່າສາກເມື່ອເຊື່ອມຕໍ່ຄືນ | ຂາດເຄືອຂ່າຍແລ້ວເຄືອຂ່າຍກັບຄືນ | ສົ່ງ StopTransaction ອັດຕະໂນມັດ, ຂໍ້ມູນຄົບຖ້ວນ |
| ການຟື້ນຟູຈາກຄວາມຜິດພາດ | ຕັດໄຟຫົວສາກໄຟແລ້ວເປີດຄືນ | ຂໍ້ມູນຟື້ນຟູຈາກການເກັບຊົ່ວຄາວ, ສາມາດລາຍງານໄດ້ປົກກະຕິ |

## **5、ຂັ້ນຕອນການຈັດຕັ້ງປະຕິບັດ**

| ໄລຍະ | ເນື້ອໃນ |
